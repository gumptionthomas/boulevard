# Milestone 4a — the steward's desk

**Scope:** the steward credential, the admin shell, the approval queue, shelf management, the shed, and settings — `DESIGN.md` §6, §8 and §13.

**Status:** design approved 17 August 2026.

---

## 1. Why this is half a milestone

`DESIGN.md` §13 assigns Milestone 4 five things: full admin, token management, and export. Bundled, that is materially larger than Milestone 3 — which ran to nine tasks, two fix rounds, and a whole-branch review that found a Critical no task-scoped review could see.

It splits cleanly because the halves share nothing but the admin shell:

- **4a, this spec — the steward's desk.** Auth, the hub, queue, shelf, shed, settings. Everything about *what is on the shelf*.
- **4b — the box and its data.** Token management (current card, force-activate, extend, revoke, regenerate, download PDF) and export. Everything about *the physical artifact and the archive*.

4a ships value on its own: it makes Milestone 2 and 3's CLI operations reachable from a phone at the box, and it retires the SQL-client editing that every acceptance run so far has needed to set `slots` or `max_age_days`.

**The CLIs stay.** `queue`/`approve`/`reject` and `shed`/`reshelve`/`release` remain, with the web as the steward's normal route. They cost nothing to keep — both already exist, both are tested, and both call the same store methods the web handlers will call, so there is no second implementation of anything. They are also the only way to administer a box over SSH with no browser, and the only practical way to drive an acceptance run into states a phone cannot reach quickly.

## 2. The credential

### Where it comes from

`DESIGN.md` §8 describes `boulevard init` printing the steward password once. That command has never been built, so today there is no way for a credential to come into being at all.

This milestone does **not** build `init`. Install has its own promise to meet — one command to a running server in under sixty seconds, with DNS verification and a docker-compose story — and dragging it into a milestone about the steward's desk would blur both. Instead:

```
boulevard steward-key [--db boulevard.db] [--slug SLUG]
```

generates a fresh key, prints it **once**, and stores only its hash. Running it again replaces the key, which is also the reset path. Milestone 5's `init` calls the same code alongside booklet generation, so nothing is built twice.

Output, in the register of the existing commands:

```
  Your steward key, shown once:

    K7Q93ZDMXR148PVBTN5A6CQXW2

  Write it down. It is not recoverable — run this
  command again to replace it.
```

### What it is

A 128-bit Crockford base32 secret, generated by the same `boulevard.RandomBase32` the token secrets and session ids already use. **Not a password the steward chooses.**

That distinction settles several questions at once. A chosen password would need a real KDF — and therefore `golang.org/x/crypto`, a dependency this project has so far avoided — because chosen passwords are low-entropy and reused across sites, so a leak harms the steward elsewhere. A generated 128-bit secret has neither problem: there is nothing to brute-force, nothing to build a rainbow table against, and no reuse to compromise.

§8 already implies this. "Prints the steward password once" is the behaviour of something generated, not something typed.

### How it is stored

**Only a SHA-256 hash**, on the `libraries` row, compared with `crypto/subtle.ConstantTimeCompare`.

Hashing here is not the same decision as §4's deliberate plaintext token secrets, and the difference is worth stating because the two rules otherwise look contradictory. A token secret is stored in plaintext because **reprinting must always work** — a lost booklet is far likelier than server compromise, and a hashed secret makes a lost booklet unrecoverable. A steward key has no artifact to reprint: losing it means generating a new one, which costs nothing. There is no reason to keep the recoverable form, so it is not kept.

Plain SHA-256 with no salt is correct for a 128-bit random input. Salting defends against precomputation across many low-entropy secrets; there is no precomputing a 128-bit random value.

**On the library row, not host-wide.** §10 requires that every setting be library-scoped so that v2's one-database-per-library storage makes ejecting a library a file copy. A host-wide credential would be the first thing that does not travel with its database.

### Before a key is set

**Every steward route returns 404**, including the login form.

Not 403, and not a "set up your steward key" page. A fresh install should not advertise a surface that is not armed, and the project already applies this instinct where it matters most — §4 requires unknown and revoked token secrets to produce byte-identical responses so that nothing confirms a guess. A 404 says only that there is nothing here.

`serve` prints a line at startup when no key is set, so a steward is told once, in the place they are already looking:

```
  No steward key set. Run `boulevard steward-key` to enable the admin.
```

## 3. The session, and a trap it must not fall into

### A separate table

Steward sessions live in **`steward_sessions`**, not the existing `sessions` table.

This is not tidiness. Milestone 3 sweeps expired rows out of `sessions` on every shelf and item render, and Milestone 3's whole privacy argument turns on that sweep being unconditional — a session row that survives is a durable record. A steward session stored in that table would either be deleted by the sweep or force the sweep to grow an exception, and an exception in a privacy mechanism is how the mechanism stops being trustworthy.

They are also different objects. A presence session carries the `token_id` of the card that minted it (§4), exists for twenty-four hours, and is meant to be forgotten. A steward session has no card behind it, lasts thirty days, and is meant to persist. Sharing a table would mean a nullable `token_id` and a kind column doing the work two tables do for free.

### Shape

```sql
CREATE TABLE IF NOT EXISTS steward_sessions (
    id         TEXT PRIMARY KEY,
    library_id TEXT NOT NULL REFERENCES libraries(id),
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL
);
```

Thirty days from creation, renewed so an active steward is not logged out mid-month.

**Renewal is not on every request.** A steward loading five admin pages should not cost five writes, and every write serialises through the one SQLite connection `SetMaxOpenConns(1)` allows. The session is extended only when **less than half its window remains** — so a steward who visits weekly is renewed roughly every fortnight, and a steward who reloads the hub twenty times in a minute is renewed once or not at all.

Expiry is checked on read **and** swept lazily on steward page loads — the same belt-and-braces pair Milestone 3 established, for the same reason: traffic drives the sweep, so the read check is what makes the interval safe.

The id is a 128-bit opaque random value, unsigned, exactly as the presence session id is and for the reason §4 records: the row is the source of truth, so a signature would add a key to store, rotate and lose while preventing no forgery the lookup already rejects.

### The cookie

`bl_steward`, distinct from `bl_session` so the two grants can never be confused for one another. `HttpOnly`. `SameSite=Strict` rather than `Lax`, because every steward route mutates and none of them should be reachable from a link someone else wrote. `Secure` when the library's base URL is `https`.

### Transport

`serve` terminates no TLS (§8), and this project expects real installs on a home LAN behind no proxy at all. Steward routes therefore **work over plain http**, and `serve` warns at startup:

```
  ! The base URL is http://calvin.local:8080
    The steward key and its cookie cross the network in the clear.
    Anyone on this network can read them. Put TLS in front of this
    box before it is reachable from outside your LAN.
```

Refusing without an override flag was considered and rejected: every localhost test and every LAN install would need the flag, and a flag everyone passes reflexively has stopped being a decision. Silence was also rejected — this is the one credential whose loss empties a shelf, and a steward deserves to be told once.

### Failed logins

Log the failure and answer with the same form and a generic message. **No lockout**: a lockout on a single-credential system is a denial-of-service anyone can trigger, and there is nothing to brute-force against 128 bits. The failure log records that an attempt happened and does **not** record the submitted value.

| `/b/{slug}/steward/i/{id}/approve` | POST | |

**The steward is not exempt from presence.** §5 is explicit that steward additions go through the same scan-and-leave flow as anyone else — the steward owns the server, but a box in a low-traffic spot otherwise drifts toward being ninety percent steward content. Nothing in this milestone adds a way to put an item on the shelf from the admin.

## 5. The hub

The landing page answers one question: **is there anything for me?**

```
  Steward · The Fairview Boulevard

  Your box
  Everything needing you, first.

  Waiting for you        3
  On the shelf           9 of 12 slots · 1 pinned
  In the shed            2 expired · 1 taken to zero
  Settings
```

A steward checks this far more often than they act on it, so its most common state is the honest one:

> **Nothing needs you.**
> Three things on the shelf, nothing waiting, nothing in the shed.

This is the same instinct §6 applies to the public empty state, which it calls arguably the most important screen in the application. The steward's empty state is the one they will see most.

Each row links to its page. The counts come from the queries that already exist — `PendingItems`, `ShelvedItems`, `ShedItems` — so the hub adds no new store method beyond the settings read it shares with the settings page.

## 6. Shelf management

### Remove sheds

A steward removing an item from the shelf sends it to the **shed**, not to `released`. A misfire is then recoverable by re-shelving, and `release` stays the deliberate second step it already is — the same soft-delete reasoning §5 gives for rejection.

It sheds with a **new reason, `removed`**, joining `evicted`, `expired` and `taken`. The shed listing already shows why an item is there, and "the steward took it down" reads differently from the three mechanical reasons: it is the only one with a person behind it, and a steward scanning the shed a week later needs to know which items they chose to remove and which the shelf shed on its own.

`boulevard.ShedReason` gains `ShedRemoved` and a `Label()` case. The label is `"you took it down"`.

### Pins

Maximum three (§5). Pinned items are never evicted, never expire, cannot be taken, and show no take control at all — all four already true, all four honoured by Milestone 3, none of them previously reachable because nothing set the flag.

A fourth pin is **refused, naming the three already pinned**, in the shape the full-shelf refusal already uses. Silently unpinning the oldest would be exactly the kind of surprise §5 warns generates steward labour.

**Pin, unpin and remove apply to `shelved` items only.** Pinning something in the shed, or removing something already removed, is refused with `ErrNotShelved` — a new sentinel in the shape of the existing `ErrNotPending` and `ErrNotShed`, so a steward can tell a mistyped id from an action that does not apply. The three existing state-transition methods all read state first for exactly this reason: "never existed" and "already handled" must be different answers.

**A pinned item still occupies a slot.** Pins are not extra shelf space — `slots` counts everything `shelved`, pinned or not, which is what makes the all-pinned case below reachable at all.

### This milestone makes a dead branch live

`ApproveItem` in `internal/store/item.go` carries this comment:

> `pinned = 0` can match nothing: Milestone 4 allows 3 pins, so a steward with `slots = 3` and three pinned items has a full shelf with nothing evictable. Today no code sets pinned, so this cannot fire; when it can, the answer is to refuse the approval with a message naming the pins, not to evict one.

**Milestone 4a is when it can fire.** Today the eviction query would return `sql.ErrNoRows` and `ApproveItem` would fail with an unhelpful wrapped error. This milestone must implement the refusal the comment describes: a sentinel error, a message naming the pinned items, and the same treatment in both the web handler and the existing CLI, which shares the store method.

Add `ErrAllPinned` to `internal/store`. `ApproveItem` returns it when the shelf is at capacity and every shelved item is pinned. The CLI prints it as a usage error; the web renders it on the queue page.

This is the single most important thing in this milestone that a reader of §6 would not predict, because it is not a feature — it is a latent failure that pinning switches on.

## 7. Settings

Six fields, per §6: name, location, `slots`, `max_age_days`, `default_copies`, approval on/off.

| Field | Rule |
|---|---|
| `name` | Required, non-empty after trimming |
| `location` | Required, non-empty after trimming |
| `slots` | Integer ≥ 1 |
| `max_age_days` | Integer ≥ 0. **Zero means never expire** — Milestone 3's sweep already reads it that way, and §11's pop-up boulevards list expiry as off |
| `default_copies` | Integer ≥ 0. Zero shelves items with nothing to take, which is legal and is the only path that reaches `ErrNoCopiesLeft` |
| approval required | Boolean |

Both text fields are stranger-free — only the steward writes them — but they render on every public page, so they are escaped by `html/template` as everything else is.

### Lowering `slots` does not retroactively evict

Setting `slots` to 5 while nine items are shelved leaves all nine on the shelf. The shelf sits over capacity, and FIFO drains it one item per approval until it fits.

The alternative — shedding four items the moment the number changes — turns a settings edit into a bulk destructive action with no confirmation and no undo. The form says what will happen instead:

> The shelf holds 9 items and you are setting 5 slots. Nothing is removed now; the oldest will move to the shed as new items are approved.

### The slug never changes

Renaming a library does **not** change its slug. `/b/{slug}/` URLs are shared, bookmarked, and — in single-library mode — the target of the root redirect. A rename that broke them would be a silent link rot with no warning.

The slug is set once at creation and is immutable. Changing it is not in this milestone and would need its own thinking about redirects, which §10 already anticipates for v2's `export-host` redirect map.

**This is enforced by the caller, and that is a trap worth naming.** `UpdateLibrary` already exists in `internal/store/library.go` and writes `slug` along with everything else — it takes a whole `boulevard.Library` and updates nine columns. The settings handler must therefore read the library, apply only the six settable fields to it, and write it back. A handler that builds a `Library` from form values alone would silently blank the slug, the base URL, and the steward key hash, because those fields would be zero.

Constructing a `Library` from form input and passing it to `UpdateLibrary` is the single easiest way to break this milestone, and it would pass any test that only checks the six fields it meant to change.

`libraries` also carries `steward_contact`, which §6 does not list among the settings and which nothing currently writes. It stays out of the form and must survive the read-modify-write like every other unlisted column.

## 8. Schema — migration 5

```sql
ALTER TABLE libraries ADD COLUMN steward_key_hash TEXT NOT NULL DEFAULT '';

CREATE TABLE IF NOT EXISTS steward_sessions (
    id         TEXT PRIMARY KEY,
    library_id TEXT NOT NULL REFERENCES libraries(id),
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL
);
```

Add as version 5 in `migrations`. **Do not also add these to `schema.sql`** — a fresh database would run both and fail on "duplicate column name". This is written on the `migration` type and has already caused one defect in this repo.

An empty `steward_key_hash` is the "no key set" state that 404s every steward route. The default makes every existing database correct without a data migration.

No `ON DELETE CASCADE` on `steward_sessions.library_id`: nothing deletes a library, and v2's storage model gives each library its own file.

## 10. Testing

Beyond ordinary coverage, and each of these covers something that has already gone wrong once in this project or is newly reachable:

- **A presence sweep must not delete a steward session.** Create one of each, run `SweepExpiredSessions`, assert the steward session survives. This is the trap the separate table exists to avoid, and it is invisible unless asserted.
- **Steward routes 404 before a key is set** — every route, including login.
- **Constant-time comparison** is used for the key. Assert the call, since a `==` would pass every behavioural test.
- **Approving into a shelf where every item is pinned** returns `ErrAllPinned` and names the pins, in both the web handler and the CLI. Newly reachable this milestone.
- **A fourth pin is refused** and names the three already pinned.
- **Remove sheds with reason `removed`**, and the item is re-shelvable afterwards.
- **Lowering `slots` sheds nothing immediately**, and the next approval evicts exactly one.
- **A rename does not change the slug**, and `/b/{slug}/` still resolves afterwards. Assert in the same test that the base URL and the steward key hash also survive the write — those are the other columns a form-built `Library` would blank, and a test that checks only the slug would miss them.
- **Pin, unpin and remove refuse a non-shelved item** with `ErrNotShelved`, distinguishably from an unknown id.
- **Non-UTC clock in every test that formats or compares a time.** The store round-trips RFC3339 in UTC; a test pinning UTC on both sides passes while the real thing is a day out. This has shipped once.
- **Never hold an open `*sql.Rows` while issuing another query.** `SetMaxOpenConns(1)` makes that a hang rather than an error; it has already cost one debugging cycle.
